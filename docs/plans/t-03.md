# T-03 — Write a booking to the sheet exactly once under contention

**Goal:** `doPost` writes a booking row exactly once per genuine request, under the ordering and
idempotency rules the team agreed, with `main.ts` reduced to wiring and every rule tested in Node
against fakes.
**Spec:** One pure `bookSlot(candidate, ports): BookResult` in `apps-script/src/domain/booking.ts`.
Ordering: structural validation → past-slot check → token verification (outside the lock) →
`tryAcquire(5000)` → inside the lock, one snapshot read, a single pass doing both the replay check
and the overlap check, then append → `release()` in a `finally`. `main.ts` builds five ports and
calls it.
**Constraints:** No new `BookingErrorCode` for lock contention — `internal_error`. No email from
the request body. No `/userinfo`, mail or logging inside the lock. No adapter import in `domain/`.
No `clasp push`, no credential, `verify` stays green with none.

## Correction to the pasted spec, found before writing any brief

This ticket's own "Idempotency" section describes a three-way rule (`booking_id` + email + slot).
That was true when T-01 was written but T-01 was revised during its own review and **merged**
with a wider rule: a replay requires `booking_id` _and every other field_ to match — `service_id`,
`customer_name` and `notes`, not only email and slot (`shared/contract.ts`, the "Idempotency replay
rule" comment, confirmed read on this branch — T-01 is merged, commit `ea5b4bb`). That file's own
header says it is the source of truth over any summary of it. T1 below implements the merged rule,
not the ticket's three-way paraphrase of it — this does not contradict this ticket's acceptance
criteria, which only assert the three-field case as a sufficient example; it closes a real gap
(T-02's merged PR's write-path stub exists but no logic yet, so nothing today depends on the
narrower reading). Flagging this now rather than let a specialist implement the stale version from
the ticket text.

Also: the "ARCHITECTURE" background pasted into this ticket says the token "travels in an
Authorization header" — the merged contract disagrees (`access_token` is a body field, confirmed by
reading `shared/contract.ts` directly). Every brief below says body field explicitly so nobody
reaches for the stale description.

## T1 — `bookSlot` and its ports

- **Specialist:** deep-implementer
- **Why that one:** the whole ticket is one ordering decision plus one correctness-critical
  loop; getting either wrong either leaks the Auth0 budget, deadlocks nothing but wastes a
  mutex wait, or — worse — tells a customer who already has a booking that their slot is gone.
- **Done when:** `apps-script/src/domain/booking.ts` exports:
  - `Clock { now(): string }`, `VerifyResult = { ok: true; email: string } | { ok: false; error:
'unauthenticated' | 'rate_limited' }`, `TokenVerifier { verify(accessToken: string):
VerifyResult }`, `Lock { tryAcquire(timeoutMs: number): boolean; release(): void }`,
    `BookSlotPorts { clock: Clock; tokenVerifier: TokenVerifier; lock: Lock; repo: BookingsRepo;
zone: Zone; stylist: string }` — `BookingsRepo`/`Zone` imported from `./bookings-repo` (T-02,
    already on `main` by the time this runs — see the dependency note above).
  - `validateBookRequest(candidate: unknown): BookRequest | ErrorResponse` — pure, checks: is a
    non-null object; `action === 'book'`; `booking_id` is a string matching
    `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i` (T-01's exact pinned
    shape); `access_token` is a non-empty string (**body field — not a header**, confirmed in
    `shared/contract.ts`); `slot_start`/`slot_end` are strings `Date.parse` accepts, with
    `slot_end`'s instant strictly after `slot_start`'s; `service_id` is a non-empty string;
    `customer_name` is non-empty after `.trim()` (store the original, untrimmed value — only the
    emptiness check trims); `notes`, if present, is a string. Any failure →
    `{ ok: false, error: 'invalid_request', message: '<names the field>' }`, no port touched.
  - `bookSlot(candidate: unknown, ports: BookSlotPorts): BookResult`, in this exact order:
    1. `validateBookRequest`; return its error untouched on failure.
    2. Past-slot check: reuse `isInPast` from `./slots` (already exists, already tested) against
       `ports.clock.now()`. `slot_in_past` on failure. **`ports.tokenVerifier` must not have been
       called yet when this fails — write the test that proves it.**
    3. `ports.tokenVerifier.verify(request.access_token)`. Map its two failure variants straight
       through as `unauthenticated` / `rate_limited`, no row written.
    4. `ports.lock.tryAcquire(5000)`; `false` → `{ ok: false, error: 'internal_error', message:
'...' }` **immediately, no `release()` call** — nothing was acquired. Never `slot_taken`
       for this path; there is deliberately no error code for contention.
    5. On success, wrap the rest in `try { ... } finally { ports.lock.release(); }`.
    6. **Exactly one** `ports.repo.loadBookingsSnapshot()` call, assigned to a local. Then one
       `for` loop over it, parsing each raw row with `parseBookingRow(raw, ports.zone)` from
       `./bookings-repo`, skipping (continue, not throw) a row that fails to parse — same
       degrade-not-crash convention T-02 already established for the read path.
    7. **The subtle part, worth getting exactly right:** inside that loop, a row whose
       `booking_id` equals the request's is decisive the instant it is found — check whether
       every other field also matches (verified email against `row.customer_email`; `slot_start`
       and `slot_end` by instant, `Date.parse(a) === Date.parse(b)`, not `rangesOverlap`, since a
       replay must be the _same_ slot, not merely an overlapping one; `service_id`;
       `customer_name`; `(request.notes ?? '') === row.notes`) and `return` right there — a full
       match returns the original `BookSuccessResponse` (status always `'requested'`, per T-01,
       even if the row's actual `status` has since changed) and writes nothing; any mismatch
       returns `invalid_request` and writes nothing. A row with a _different_ `booking_id` is
       only ever a candidate for the overlap check (skip if `row.status === 'cancelled'`; record
       `rangesOverlap({ start: row.slot_start, end: row.slot_end }, { start: request.slot_start,
end: request.slot_end })` from `./slots` in a boolean, but **do not return on finding an
       overlap** — keep scanning). The reason: a snapshot can hold both an unrelated overlapping
       row _and_, later in the same array, the request's own replay row, and the replay must win.
       Only after the loop finishes with no `booking_id` match does the recorded overlap flag
       decide `slot_taken` vs. proceeding to append.
    8. Append: build the `BookingRow` (`booking_id`, `created_at` from
       `toSlotIso(new Date(ports.clock.now()), ports.zone)` — reuses T-02's own instant-to-salon-
       local formatter — `slot_start`/`slot_end` echoed verbatim from the request, `service_id`,
       `stylist: ports.stylist`, `customer_name`, `customer_email` from the verifier's `email`,
       `status: 'requested'`, `notes: request.notes ?? ''`), call `ports.repo.append(row)`, return
       `BookSuccessResponse` echoing `booking_id`/`slot_start`/`slot_end` from the request.
  - `npm run typecheck` and `npm run lint` pass (no `any`, matching `CONVENTIONS.md`).
- **Tests (`booking.spec.ts`)**, fakes only, no real timers, covering literally every filed
  criterion plus the spec's named extras: well-formed request writes exactly one row with
  `status: 'requested'`; two different-`booking_id` requests targeting the same slot (call
  `bookSlot` twice against one mutable fake snapshot — append the first call's row into the
  array the second call's fake `loadBookingsSnapshot` returns) → first succeeds, second gets
  `slot_taken`; same `booking_id`+email+slot replay → original success, `append` spy not called;
  same `booking_id`+email, different slot → `invalid_request`; malformed `booking_id` →
  `invalid_request`, no port called at all; past slot → `slot_in_past`, verifier spy not called;
  failed verification → `unauthenticated`, no append; lock unavailable → `internal_error`, never
  `slot_taken`, `append` not called; `customer_email` written is the verifier's `email`, never
  anything from the candidate (there is no email field on `BookRequest` to even smuggle one in —
  assert the written row's `customer_email` equals the fake verifier's configured email); verifier
  not called when structural validation fails; `loadBookingsSnapshot` called exactly once per
  `bookSlot` call (`vi.fn` call-count assertion); **the overlap-before-replay-in-snapshot-order
  case from step 7** — a fake snapshot with an unrelated overlapping row _before_ the request's
  own replay row still returns the original success, not `slot_taken`.
- **Parallel:** yes — new files only.
- **Depends on:** nothing to start (ports are self-defined); needs T-02 merged to typecheck clean
  against `BookingsRepo`/`Zone`/`parseBookingRow`/`isInPast`/`rangesOverlap` — I check that before
  dispatching and pull `main` first if needed.

## T2 — Fill in `SheetBookingsRepo.append`

- **Specialist:** implementer
- **Why that one:** real logic (column mapping, range construction, the number-format ordering),
  but no design tension — the shape is pinned above.
- **Done when:** `apps-script/src/adapters/sheet-bookings-repo.ts`'s `append(row: BookingRow):
void` replaces the `throw new Error('implemented in T-03')` stub: opens the `Bookings` sheet
  (same `SHEET_TAB_NAMES.bookings` lookup `loadBookingsSnapshot` already uses — reuse the same
  not-found error), computes `values = BOOKINGS_COLUMNS.map((c) => row[c])`, computes the next
  empty row as `sheet.getLastRow() + 1`, builds two ranges on that row — the three datetime
  columns (`created_at`/`slot_start`/`slot_end`, found via `BOOKINGS_COLUMNS.indexOf`, not a
  hardcoded column letter) and the full row — and calls the new exported `writeFormattedRow`
  (below) with them. Also add, in the same file:
  ```ts
  export interface FormattableRange {
    setNumberFormat(format: string): void;
  }
  export interface ValueRange {
    setValues(values: unknown[][]): void;
  }
  export function writeFormattedRow(
    dateRange: FormattableRange,
    rowRange: ValueRange,
    values: unknown[]
  ): void {
    dateRange.setNumberFormat('@');
    rowRange.setValues([values]);
  }
  ```
  `append` calls `writeFormattedRow(sheet.getRange(nextRow, firstDateCol, 1, 3), sheet.getRange(nextRow, 1, 1, BOOKINGS_COLUMNS.length), values)`.
- **Tests (`sheet-bookings-repo.spec.ts`, new):** one test, plain object fakes implementing
  `FormattableRange`/`ValueRange`, asserting `setNumberFormat` is called before `setValues` (an
  array recording call order, asserted `toEqual(['format', 'setValues'])`). Do not attempt to
  test `append` itself or `loadBookingsSnapshot` — both touch `SpreadsheetApp` and have no Node
  equivalent, same boundary `CONVENTIONS.md` already states and T-02 already followed.
- **Parallel:** yes alongside T1, T3, T4 — different files. Needs T-02 merged (this file exists
  only on T-02's branch right now).
- **Depends on:** T-02 merged. Not on T1.
